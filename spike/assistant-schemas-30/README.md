# AssistantSchemas pre-implementation spike — manual test plan

Branch: `spike/assistant-schemas-manual`. This folder contains hand-written Swift artifacts to verify three runtime behaviors of `@AppIntent(schema: ...)` that can't be answered from Apple's docs alone. Bypasses our config plugin entirely — these are throwaway iOS-level verification files.

Findings get recorded back in `.plan/08-assistant-schemas-research.md` § Spike findings table.

## Files in this folder

- `AppShortcutsBridge.generated.spike.swift` — modified version of the auto-generated provider with three spike intents inlined: `SpikeSearchIntent` (`.system.search`), `SpikeAssistantOnlyIntent` (`.camera.stopCapture` + `isAssistantOnly = true`), `SpikeControlIntent` (vanilla AppIntent control). All wired into `ExpoAssistantAppShortcuts.appShortcuts`.
- `README.md` — this file

**Why all in one file?** A separate Swift file would need manual Xcode project registration. Inlining into the existing generated file (already in the project) bypasses that step entirely — cleaner for throwaway spike code.

`example/ios/` is gitignored (regenerated by `expo prebuild`), so we keep the spike artifact here and copy it into place when running.

**Bonus finding from initial build attempt:** Apple enforces *per-schema-id uniqueness at the binary linker level*. Two intents in one app cannot both conform to the same schema (e.g., two `.system.search`) — the build fails with `Only 1 type per app allowed to conform to Assistant schema identifier 'X'`. The codegen for #30 needs prebuild validation rejecting duplicate `schema:` values across `appShortcuts[]`. Why this matters: it's a hard binary-level constraint, not a soft macro warning — we must catch it before xcodebuild does.

## Setup procedure

```bash
# From /Users/matthew/Github/expo-assistant
cd example
bun install

# Regenerate iOS baseline (writes a fresh AppShortcutsBridge.generated.swift)
bunx expo prebuild --platform ios --clean

cd ios && pod install --silent && cd ..

# Overwrite the freshly-generated provider with the spike version
cp ../spike/assistant-schemas-30/AppShortcutsBridge.generated.spike.swift ios/expoassistantexample/AppShortcutsBridge.generated.swift

# Build + install on simulator. Replace "iPhone 17" with your booted device name
# (see `xcrun simctl list devices | grep Booted` for what you have).
open -a Simulator
bunx expo run:ios --device "iPhone 17"
```

After app launches, **force-kill it** to ensure linkd re-ingests metadata (Cmd+Shift+H to home, then swipe up). Re-install for clean state:

```bash
xcrun simctl uninstall booted expo.modules.assistant.example
xcrun simctl install booted "$(find ~/Library/Developer/Xcode/DerivedData -name 'expoassistantexample.app' -path '*Debug-iphonesimulator*' | head -1)"
xcrun simctl launch booted expo.modules.assistant.example
```

Then kill the app and proceed to tests.

## Test Q1: voice extraction on schema-conformant intents in AppShortcutsProvider

**Goal:** verify `@AppIntent(schema: .system.search)` intents referenced from `AppShortcut` phrases are voice-invokable via Siri the same way vanilla AppIntents are. The ADR cited this as medium-confidence — Apple docs imply yes, but the explicit confirmation isn't in writing.

### Procedure

1. Open the Shortcuts app on the simulator
2. Tap "All Shortcuts" → look for the "expo-assistant-example" app section
3. **Expected:** four shortcut tiles appear — Open Project, Spike Control, Spike Search, Spike Assistant Only
4. Tap "Spike Search" — verify it invokes (Library tap doesn't need voice, just confirms the intent is wired)
5. Activate Siri (Cmd+Option+S in simulator, hold side button on device)
6. Say: **"Run spike search in expo-assistant-example"**
7. **Expected:** Siri invokes `SpikeSearchIntent.perform()` — check Console.app filtering for `[expo-assistant-spike]`:
   ```
   [expo-assistant-spike] SpikeSearchIntent.perform() bridge latency: <N>ms
   ```
8. Repeat with the control: "Run spike control in expo-assistant-example" — verify `SpikeControlIntent` fires

### Record

- [ ] Schema intent visible in Shortcuts.app Library?
- [ ] Schema intent visible in Spotlight when typing "spike search"?
- [ ] Did Siri match the phrase and invoke `SpikeSearchIntent.perform()`?
- [ ] If no: what did Siri say / show? Phrase not recognized? Wrong app? Silent failure?
- [ ] User-visible difference between schema intent invocation and control intent invocation?

## Test Q3: `isAssistantOnly = true` interaction with `AppShortcutsProvider` phrase registration

**Goal:** ADR predicted that `isAssistantOnly = true` removes the intent from Shortcuts.app and Spotlight, but it's unclear whether iOS still honors the `AppShortcut` phrase registration for Apple Intelligence routing — i.e., whether the AppShortcut entry is silently dropped or kept with AI-only invocation.

### Procedure

1. Continue from Q1 setup (app installed, killed)
2. Shortcuts app → All Shortcuts → expo-assistant-example
3. **Expected:** "Spike Assistant Only" should be ABSENT (since `isAssistantOnly = true`)
4. Spotlight (swipe down on home) → search "spike assistant only"
5. **Expected:** no result, or only a web-search fallback
6. Activate Siri → say: **"Run spike assistant only in expo-assistant-example"**
7. **Three possible outcomes:**
   - (A) Invokes `SpikeAssistantOnlyIntent.perform()` (`[expo-assistant-spike] SpikeAssistantOnlyIntent.perform() fired` appears in log)
   - (B) Siri says "I don't have an app called that" / falls back to web search
   - (C) Opens the app but doesn't fire the intent

### Record

- [ ] Absent from Shortcuts.app Library? (expected: yes)
- [ ] Absent from Spotlight? (expected: yes)
- [ ] Siri voice outcome: A / B / C
- [ ] If A: AppShortcutsProvider + isAssistantOnly are independently configurable surfaces
- [ ] If B or C: AppShortcut registration silently dropped when isAssistantOnly = true. Plugin should warn on this combination

## Test Q4: cold-start latency for `perform()` when JS bridge needs to come up

**Goal:** measure how long the RN bridge takes to become responsive when our app was force-killed and Siri invokes the intent. Informs the runbook's latency-budget guidance.

### Procedure

1. From Q1 setup, ensure app has been launched once (JS bridge initialized)
2. **Force-kill the app:** swipe up to multitasker, swipe app card away
3. Wait 10 seconds
4. Activate Siri → say: **"Run spike control in expo-assistant-example"**
5. (App may or may not visibly come to foreground depending on `openAppWhenRun` — not set on spike intents intentionally, to measure the no-foreground path)
6. Console.app: filter for `[expo-assistant-spike]` — look for `SpikeControlIntent.perform() bridge latency: <N>ms`
7. **The logged latency** = time between `perform()` start and `emitIntent` returning. Does NOT capture whether JS handler actually received it. To measure end-to-end:
   - Watch `App.tsx` console for the existing `onIntentInvoked` handler firing
   - End-to-end latency = Siri "OK" sound → JS log appears
8. Optional: edit `SpikeControlIntent` to add `public static var openAppWhenRun: Bool = true`, rebuild, repeat the test to compare

### Record

- [ ] Bridge latency from `perform()` log: __ ms
- [ ] Did `emitIntent` reach the JS handler? (check App.tsx console)
- [ ] If yes: end-to-end cold-start latency: __ ms
- [ ] If no: bridge didn't survive cold-start — we need `openAppWhenRun: true` for schema intents
- [ ] App visibly foregrounded? Yes / No
